# LESEDI — survivor-controlled safety orchestration (development build)

Django + Django REST Framework + PostgreSQL + Redis/Celery, run with Docker Compose.
**Simulation mode only:** nothing is ever sent to real people, and no emergency service is contacted.

> **Not a substitute for emergency services.** If you are in danger, contact your local emergency services.

## Install on Kali Linux

All commands run in a normal terminal as your own user.

### 1. Install Docker and Git

```bash
sudo apt update
sudo apt install -y docker.io git
sudo apt install -y docker-compose-plugin || sudo apt install -y docker-compose
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
newgrp docker          # or log out and back in so the group applies
docker --version
docker compose version || docker-compose version
```

If only `docker-compose` (with a hyphen) works, use it wherever this README says `docker compose`.

### 2. Configure

```bash
cd lesedi                                   # the project folder
cp .env.example .env
SECRET=$(python3 -c "import secrets; print(secrets.token_urlsafe(64))")
DBPASS=$(python3 -c "import secrets; print(secrets.token_hex(16))")
sed -i "s|^DJANGO_SECRET_KEY=.*|DJANGO_SECRET_KEY=${SECRET}|" .env
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=${DBPASS}|" .env
mkdir -p private_storage
export LESEDI_UID=$(id -u) LESEDI_GID=$(id -g)
```

Add the two `export` values to `~/.bashrc` (or re-run them in each new terminal), otherwise files created in
the project folder may be owned by the wrong user. Never commit `.env`.

### 3. Build

```bash
docker compose build
```

### 4. Check and apply migrations

```bash
docker compose run --rm web python manage.py check
docker compose run --rm web python manage.py makemigrations --check --dry-run
```

If the second command reports **"No changes detected"**, continue. If it lists changes, the hand-written
migrations differ from the models. Generate corrections and review them:

```bash
docker compose run --rm web python manage.py makemigrations
git diff --stat 2>/dev/null || ls */migrations
```

Then apply:

```bash
docker compose run --rm web python manage.py migrate
```

### 5. Start the services

```bash
docker compose up -d
docker compose ps
curl -s http://localhost:8000/healthz
```

Expected: `{"status": "ok", "database": true}`. The site is at <http://localhost:8000> (bound to localhost only).
Services: `web` (Django dev server), `worker` (Celery), `beat` (Celery schedule that drives escalation),
`db` (PostgreSQL 16), `redis`.

Logs: `docker compose logs -f web worker beat`. Stop: `docker compose down`.

### 6. Load the fictional demo and sign in

```bash
docker compose exec web python manage.py seed_demo
```

It prints the demo login and a random password. Sign in at <http://localhost:8000/accounts/login/>.
The demo only runs with `DJANGO_DEBUG=1` and `LESEDI_NOTIFICATION_MODE=simulation`. All names are fictional.

Create your own administrator (follow the prompts, which ask for an email and display name):

```bash
docker compose exec web python manage.py createsuperuser
```

Django admin is at `/admin/` unless you change `DJANGO_ADMIN_URL`.

### 7. Run the tests

```bash
docker compose run --rm web pytest
```

Useful variants:

```bash
docker compose run --rm web pytest tests/test_demo_scenario.py
docker compose run --rm web pytest tests/test_guardian.py -k "concurrent or duplicate"
docker compose run --rm web pytest -x --pdb          # stop at the first failure
```

Tests create a separate `test_lesedi` database, force simulation mode and use a temporary vault folder.
Please send me the first failures you see; some are likely, since the suite has never run.

Static checks that need no Docker or Django:

```bash
python3 -I scripts/check_names.py
python3 -I scripts/check_static.py
```

### 8. Deployment checks (not a deployment)

```bash
KEY=$(docker compose run --rm web python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())")
docker compose run --rm -e DJANGO_DEBUG=0 -e EVIDENCE_ENCRYPTION_KEYS="$KEY" web python manage.py check --deploy
docker compose run --rm web pip-audit -r requirements.txt
```

Passing `check --deploy` does not replace a security review. The compose file is for development only.
Production needs HTTPS, a managed secret store, **backed-up** evidence encryption keys (losing the key makes
stored evidence unreadable), `gunicorn` behind a TLS proxy, and a security and legal review.

### Backup and restore (development data)

```bash
docker compose exec -T db pg_dump -U lesedi lesedi > lesedi-backup.sql
docker compose exec -T db psql -U lesedi lesedi < lesedi-backup.sql
tar czf vault-backup.tgz private_storage        # keep this together with EVIDENCE_ENCRYPTION_KEYS
```

## First run of the community feed

The `community` app is new, so it has no migration yet. Generate and apply it, then run its tests:

```bash
docker compose run --rm web python manage.py makemigrations community
docker compose run --rm web python manage.py migrate
docker compose run --rm web pytest tests/test_community.py
docker compose up -d --build        # restarts web, worker and beat so the daily purge task is picked up
```

Moderators are created by an administrator: sign in to `/admin/` with the superuser, open the person under
Users and set their **Role** to Moderator. Nobody can give themselves that role. Moderators see only
community submissions. Pages: `/community/` (feed), `/community/moderation/` (queue, moderators only),
`/community/witness/` (private concern). Retention: `python manage.py purge_community`, also run daily by `beat`.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `permission denied ... docker.sock` | Run `newgrp docker` or log out and in; confirm with `id`. |
| `set POSTGRES_PASSWORD in .env` | Step 2 not done, or `.env` is not in the folder you run compose from. |
| `password authentication failed for user "lesedi"` | You changed `POSTGRES_PASSWORD` after the database volume existed. Development only: `docker compose down -v` (**deletes all dev data**), then start again. |
| `port is already allocated` on 8000 | Stop what uses it (`ss -ltnp \| grep 8000`) or change the port mapping in `docker-compose.yml`. |
| `relation "..." does not exist` | Migrations not applied: step 4. |
| `No matching distribution found` / pin not found during build | A pinned version does not exist or conflicts. Edit the line in `requirements.txt` to the nearest released version, then rebuild with `docker compose build --no-cache`. |
| `ImproperlyConfigured: DJANGO_SECRET_KEY` or `EVIDENCE_ENCRYPTION_KEYS` | Only raised when `DJANGO_DEBUG=0`. Set both in `.env`. |
| CSRF verification failed | Use one hostname consistently (`localhost` or `127.0.0.1`) and keep it in `DJANGO_CSRF_TRUSTED_ORIGINS`. |
| Files in the project folder owned by root | Export `LESEDI_UID`/`LESEDI_GID` (step 2) and fix with `sudo chown -R "$USER": .`. |
| `PermissionError` writing `private_storage` | `sudo chown -R "$USER": private_storage`. |
| Guardian never escalates to the backup | `docker compose ps` must show `worker` **and** `beat` running; read `docker compose logs beat worker`. |
| Password-reset email not arriving | By design in development: emails print to `docker compose logs web`. |
| Test database errors | The `db` container must be healthy: `docker compose ps`. |
